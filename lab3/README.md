# Лабораторная работа 3 Вариант 3

Параллельная сортировка слиянием на C с нативными POSIX-потоками.
Один процесс; лимит `-t` включает главный поток. Предназначена для Linux
и macOS. Высокоуровневых библиотек в программе нет.

## Сборка и запуск

Нужны GCC или Clang и Make. В Ubuntu: `sudo apt install build-essential procps strace`.

```sh
make
./build/mergesort -n 1000000 -t 4
./build/mergesort -i evidence/input.txt -t 3 --print
./build/mergesort --help
```

Файл содержит целые десятичные числа типа `int`, разделённые пробельными
символами; размер определяется по концу файла. Пустой файл и `-n 0` допустимы.
Варианты генерации: `--kind random`, `sorted`, `reverse`, `equal`.
Ключ `-s` задаёт зерно генератора, по умолчанию 42: один вход можно повторить
для разных лимитов. Успех обозначается `sorted=OK` и кодом выхода 0;
ошибка - сообщением в stderr и кодом 1. `--print` печатает весь результат.

`seconds` - длительность сортировки, включая создание и ожидание потоков,
по CLOCK_MONOTONIC. Генерация, выделение памяти, контроль порядка и печать
не входят в замер. `peak` - внутренний максимум одновременно исполняющихся
функций потоков с учётом главного. Точный список потоков ОС проверяется
отдельно. Контрольная сумма помогает сравнивать запуски; при проверке
также сравнивался весь результат с независимым эталоном.

## Устройство решения

- `src/main.c`: подготовка памяти, измерение, проверка порядка, освобождение.
- `src/input.c`, `src/input.h`: аргументы запуска, чтение файла, генератор.
- `src/sort.c`, `src/sort.h`: слияние, рекурсия, создание потоков и синхронизация.
- `evidence/`: фактические логи и сырые измерения.
- `report.docx`: отчёт по предоставленному шаблону.

Каждой рекурсивной задаче передаётся бюджет `b`. Левая половина получает
`b/2` потоков, правая - `b-b/2`. Для левой создаётся один новый поток,
правую обрабатывает текущий. После `pthread_join` половины сливаются.
При бюджете 1 или размере меньше 2048 выполняется обычная последовательная
сортировка слиянием. Порог предотвращает создание потоков для мелких задач.
Максимум ключа `-t` равен 256, что ограничивает избыточный расход стеков.

Потоки записывают в непересекающиеся участки исходного и вспомогательного
массивов. Родитель сливает их только после join. Мьютекс защищает счётчики
и строки диагностического вывода; он не удерживается при сортировке или join.
Вспомогательный массив выделяется один раз, расход памяти - O(n) плюс стеки
потоков. Время обычной сортировки - O(n log n). Финальное слияние последовательно.

Если создание потока не удалось, ошибка передаётся вверх по рекурсии;
уже созданные соседние потоки дожидаются через join. Память освобождается
в main после завершения всех ветвей. Неисправимые ошибки самих примитивов
синхронизации завершают весь процесс с диагностикой: продолжать работать
с недостоверным состоянием мьютекса или потока нельзя, ресурсы процесса
освобождает ОС.

## Демонстрация потоков средствами ОС

Linux, в одном терминале:

```sh
./build/mergesort -n 1000000 -t 4 --verbose --hold 10 &
sort_pid=$!
ps -L -p "$sort_pid" -o pid,tid,nlwp,stat,comm
ls "/proc/$sort_pid/task"
wait "$sort_pid"
```

Если ps выполнен сразу после запуска, потоки ещё могут создаваться.
Дождитесь строки `live=4`, затем выполните команду ps ещё раз:
она должна показать четыре потока, включая главный.
На macOS используется `ps -M -p "$sort_pid"`.
`--hold` удерживает потоки в листьях рекурсии для наблюдения, применяется
только в демонстрации. Для измерения времени этот ключ не использовать.
Фактические логи находятся в `evidence/demo.log` и `evidence/threads.log`;
имя локальной учётной записи заменено нейтральной меткой.

## Трассировка на Linux

```sh
strace -f -tt -e trace=clone,clone3,futex,mmap,munmap \
  -o evidence/trace.log \
  ./build/mergesort -n 1000000 -t 4 --verbose --hold 1
```

`-f` включает потоки, `-tt` показывает время вызовов. Создание потока видно
как `clone` или `clone3`. Ожидание в `pthread_join` обычно видно по `futex`.
Мьютекс без конкуренции может обойтись без системного вызова. `clock_gettime`
часто обслуживается через vDSO и потому может отсутствовать в трассировке.

На Ubuntu 24.04 LTS при `-t 4` команда `ps -L` показала четыре потока одного
процесса, включая главный. В трассировке видны три успешных вызова `clone`
и ожидание завершения рабочих потоков через `futex`.

## Проверки и исследование

Ранее выполнены проверки на macOS arm64 с Apple Clang 21: 147 запусков
обычной сборки, 147 с ASan/UBSan, 147 с ThreadSanitizer и 7 сценариев отказов.
Проверочные инструменты запускались отдельно от сдаваемого проекта.
Сводка результатов - `evidence/validation.txt`.

Повторить отдельный замер можно так, меняя лимит -t и состав --kind:

```sh
./build/mergesort -n 4000000 -t 1 -s 42 --kind random
./build/mergesort -n 4000000 -t 4 -s 42 --kind random
```

В исследовании четыре размера, четыре состава массива и лимиты 1, 2, 4, 8.
Для каждой комбинации: прогрев и пять замеров; в таблицах используется медиана.
Сырые данные - `benchmark_raw.csv`, сводка - `benchmark_summary.csv`, параметры
среды - `benchmark_environment.txt`, всё в `evidence/`.
Ускорение `S(p)=T(1)/T(p)`, эффективность относительно лимита `E(p)=S(p)/p`.
Для 1000 элементов фактически работает один поток при любом лимите из-за
порога; уменьшение E в этом случае описывает неиспользованный лимит.
Для остальных размеров наблюдались пики, равные заданным лимитам.
ЦП не закреплялись, фоновая нагрузка и неоднородные ядра могут влиять на время.
